# mica-ppocr、RapidOCR4j 与 Xberg 性能、资源与识别效果对比评测报告

> **测试环境与基准说明**：
> - **Java 版本**：OpenJDK 21 (Java 21 LTS，开启 `--enable-preview --enable-native-access=ALL-UNNAMED`)
> - **框架体系**：Spring Boot 3.5.6 + Log4j2 (非 Logback 模式)
> - **模型架构**：PP-OCRv6 `tiny` 官方 ONNX 模型（三家引擎共用同一套 det/rec 权重与字典）
> - **基准配置**：并发度 `C=2`（同时支持单线程 C=1、高并发 C=4 梯度对比），单算子线程 `intraOpNumThreads=1`
> - **引擎版本**：`mica-ppocr-core 1.1.6`、`rapidocr4j 3.9.2`、`xberg-jdk21 1.3.9`（`paddle-ocr` 后端）
> - **测量口径**：同一进程内顺序执行，单次运行结果；重复运行 QPS 波动约 ±15%，Xberg 的绝对延迟波动更大，请以量级而非末位数字做判断
> - **生成时间**：2026-10-14 22:43:39

## 一、 核心选型结论摘要

| 评测维度 | mica-ppocr | RapidOCR4j | Xberg | 选型建议与差异分析 |
| :--- | :--- | :--- | :--- | :--- |
| **并发吞吐 (QPS)** | 见下表实测 | 见下表实测 | 见下表实测 | 三家均基于 ONNX Runtime，相同 tiny 模型与线程配置下吞吐高度接近 |
| **内存管理 (Native RSS)** | 稳定无泄漏 | 稳定无泄漏 | 稳定无泄漏 | 进程物理内存主要由 ONNXRuntime/OpenCV Native 堆占用，JVM 堆仅占小部分 |
| **模型管理与依赖** | 需配置模型路径与字典 | **内置默认模型**，开箱即用 | **绑定库 + ORT + 模型全部内置于 jar**，首次落地后复用 | RapidOCR4j / Xberg 开箱即用；mica-ppocr 支持灵活切换 tiny/small/medium 档位 |

| **坐标与定位精度** | 文本行级四点多边形 | **单字/英文词级精确坐标** | 行 / 词级 OCR 元素（`ocrElements`）与几何信息 | 需要字级高亮/双层 PDF 重建推荐 `RapidOCR4j` |
| **生态与框架集成** | **Spring Boot 官方 Starter** | 独立 Java SDK | 独立 Java SDK（JDK 21 + preview） | Spring 体系推荐 `mica-ppocr`，跨语言/多格式文档推荐 `Xberg`，非 Spring 且需 JDK 17 推荐 `RapidOCR4j` |

> 说明：冷启动在同一 JVM 内按 `Xberg → mica-ppocr → RapidOCR4j` 的顺序依次测量，先测量的引擎需承担 OpenCV / ONNX Runtime 等共享原生库的一次性加载成本。
> Xberg 多出的「原生资源落地」是首次把 jar 内的绑定库、ONNX Runtime 与模型复制到 `runtime-dir` 的一次性成本，同机重复运行时该列为 0（文件按大小比对后全部 reused）。
> Xberg 的 det/rec/角度分类 ONNX 会话在首次 `extract` 时惰性创建，因此它的「首帧推理」包含三个会话的建立成本，其余两家在引擎实例化阶段就完成了会话创建。

## 六、 生产环境选型综合建议

1. **如果你的项目是 Spring Boot / 企业微服务，且需要处理证件、发票、营业执照等结构化数据**：
   - **首选 `mica-ppocr`**：开箱提供 Spring Boot Starter，内置 9+ 种常见凭证解析器，支持整图 4 方向纠偏（处理手机倒拍/横拍），模型与代码解耦方便升级。

2. **如果你的项目是通用工具库、或者需要精确字/词级高亮标注、或需要兼容 JDK 17 及以下**：
   - **首选 `RapidOCR4j`**：开箱内置模型，无需配置模型文件路径，支持单字/词级细粒度坐标输出，支持调用级热参数覆盖（`ParamConfig`）。

3. **如果你的项目需要多格式文档理解（PDF/Office/图片统一入口），并希望一次拿到版面、表格、分块与关键词**：
   - **首选 `Xberg`**：绑定库、ONNX Runtime 与 PP-OCRv6 模型全部打包在 `xberg-jdk21` jar 内，`Xberg.extract` 单入口覆盖图片/PDF/Office；代价是必须运行在 **JDK 21 且开启 `--enable-preview`** 的进程上，首次调用需把原生资源落地到 `runtime-dir`。

4. **高并发部署与资源配置建议**：
   - OCR 计算主要消耗 CPU 和 Native 物理内存（RSS），JVM 堆占用极少。
   - 容器化部署时，**内存限制（Memory Limit）必须以 Native 物理内存为基准**（建议每路并发预留 300MB~500MB 物理内存），不能仅依赖 `-Xmx`。
   - 多线程并发时建议将 `intraOpNumThreads` 设为 `1` 或 `CPU物理核数/并发路数`，避免算子线程超订导致吞吐下降。
   - 同一 JVM 内混跑多个 OCR 引擎时，Windows 会按模块名复用已加载的 `onnxruntime.dll`；本工程先让 Xberg 落地并加载其自带 ONNX Runtime，再启动其余引擎，保证三者共享同一份原生运行时。

## 七、 复现方式

```bash
# 1. 用 JDK 21 运行（Xberg 绑定库依赖 preview 特性，JDK 17 无法加载）
export JAVA_HOME=/path/to/jdk-21

# 2. 直接启动，CommandLineRunner 会自动跑完整基准并覆写本报告
mvn spring-boot:run

# 3. 只想跑测试不跑基准
mvn test -Dtest=OcrCompareTest
```

- 运行参数由 `spring-boot-maven-plugin` 注入：`--enable-preview --enable-native-access=ALL-UNNAMED -Dxberg.runtime.dir=target/xberg-runtime`，IDE 中直接运行主类时需手工补上。
- Xberg 的绑定库 / ONNX Runtime / PP-OCRv6 模型全部来自本地仓库的 `io.xberg.jdk21:xberg-jdk21:1.3.9`，首次运行落地到 `target/xberg-runtime`，也可用环境变量 `XBERG_RUNTIME_DIR` 改写。
- 调整基准规模：`ocr.benchmark.requests-per-bench`、`ocr.benchmark.warmup-requests`、`ocr.benchmark.stability-requests`、`ocr.benchmark.concurrencies`。
- 只做单测不跑基准：`ocr.benchmark.auto-run-on-startup=false`。
