## 四、 Xberg 并发吞吐偏低与扩展性不足的成因分析

### 4.1 实测扩展性对比（中图-证件卡片 800x500）

| 引擎名称 | C=1 QPS | C=4 QPS | C=1→C=4 放大倍数 | C=1 平均延迟 (ms) | C=4 平均延迟 (ms) | 延迟增幅 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| `mica-ppocr` | 4.78 | 7.36 | **1.54x** | 209 | 510 | +144% |
| `RapidOCR4j` | 1.92 | 7.41 | **3.86x** | 521 | 505 | -3% |
| `Xberg` | 2.02 | 3.27 | **1.62x** | 494 | 1170 | +137% |

三家的吞吐都会随并发度上升，但 mica-ppocr / RapidOCR4j 接近线性（4 路并发约 3.2 倍、延迟只涨 20% 以内），Xberg 的放大倍数明显更低、平均延迟被并发推高得更狠。

### 4.2 成因一：PaddleOCR 推理会话被互斥锁持有，OCR 阶段无法跨请求并行

Xberg 官方 OCR 指南明确写道：**「PaddleOCR 的页面不并发执行 —— ONNX session 被 mutex 持有，因此线程预算全部用于算子内并行（intra-op parallelism），总墙钟时间 ≈ 页数 × 单页推理时间」**。

也就是说，Xberg 进程内每次 `Xberg.extract` 的推理段落是串行的：并发请求只能重叠 OCR 之外的预处理/后处理，推理段落排队使平均延迟随并发度单调上升。这解释了 4.1 中「放大倍数低 + 延迟增幅大」的组合特征。

### 4.3 成因二：线程预算是进程级共享，且默认被硬上限截断

`ExtractionConfig.concurrency.max_threads` 是**进程级共享预算**（同时约束 Rayon 全局池、ONNX Runtime intra-op 线程与批量子任务）。参考文档说明其默认规则为：

- 未设置时有效预算 = `min(检测到的 CPU 核心数, 8)`；核数 > 8 且无 Linux cgroup CPU 配额时，**多出来的核不会被使用**，且首次解析会打出 WARN 提示。本机 16 逻辑核，默认只用到 8 个。
- `max_concurrent_ocr` 未设置时「跟随 `max_threads`，并再按主机空闲内存可承载的会话数下调」，而且该限制在**进程内首次抽取时固定**、之后不可更改。

后果是：不显式配置时，Xberg 的并发额度由「启动瞬间的空闲内存」决定，同一份配置不同次运行的结果会明显分叉（本机对同一默认配置重复测量，C=4 吞吐在 6.5~10.5 QPS 之间摆动，波动幅度超过任何一项调优带来的收益）。

### 4.4 成因三：检测输入尺寸与另外两家不一致

Xberg 的 `det_limit_side_len` 默认 **1024**，而本工程 mica-ppocr / RapidOCR4j 走的 `max-side-limit` 是 **960**。在 1600x2200 的大图上，Xberg 的检测分辨率更高（像素量约多 `(1024/960)² ≈ 1.14` 倍），叠加其文档解析流水线的固定开销，单页平均延迟明显高于另外两家。该项属于配置口径不一致，可对齐。

### 4.5 成因四：真正不对等的是线程语义，而不是「线程给少了」

把三者放到同一个进程级线程预算下（`intra-op-num-threads=16` + Xberg `max-threads=16`）另跑一组对照实验，中图-证件卡片 C=4 的结果与本轮报告对比：

| 引擎名称 | 统一线程预算=16 的 C=4 QPS（对照实验） | 本轮报告 C=4 QPS |
| :--- | :---: | :---: |
| `mica-ppocr` | 5.03 | 7.36 |
| `RapidOCR4j` | 3.16 | 7.41 |
| `Xberg` | **9.36** | 3.27 |

> 对照实验与本轮报告是同一台机器上的两次独立运行，绝对值仅供横向比较。

结论很清晰：

1. `mica-ppocr` / `RapidOCR4j` 的 `intraOpNumThreads` 是**会话级**参数，C 路并发各自持有会话，实际线程数 = `C × intraOp`；设成 16 后就是 4 × 16 = 64 线程抢 16 个核，严重超订，吞吐反而掉到各自合理配置的 1/4 ~ 1/6。
2. `Xberg` 的 `max_threads` 是**进程级共享**预算，不会随并发度翻倍，所以给足预算它是三者中扩展性最好的。
3. 因此「Xberg 并发效果差」并不等于线程配少了：在**同一台机器各自的合理配置**下，它单页延迟本身就高（mutex 串行 + 文档流水线固定开销）；而一旦按会话级语义去对比，把三家的线程数字强行设成一样，反而会把另外两家打垮。

## 五、 三引擎 OCR 参数对齐与 Xberg 调优

### 5.1 OCR 语义参数逐项对齐

三家使用同一套 PP-OCRv6 `tiny` 权重与字典，检测/识别超参与批次完全一致，因此吞吐与精度差异来自运行时行为，而不是模型或阈值口径。

| OCR 参数 | 工程配置键 | mica-ppocr | RapidOCR4j | Xberg |
| :--- | :--- | :--- | :--- | :--- |
| 检测模型 | `ocr.model.det-model-path` | `det.onnx` | 同左 | jar 内置 `v6/det/tiny/model.onnx` |
| 识别模型 | `ocr.model.rec-model-path` | `rec.onnx` | 同左 | jar 内置 `v6/rec/tiny/model.onnx` |
| 识别字典 | `ocr.model.dict-path` | `dict.txt` | 同左 | jar 内置 `v6/rec/tiny/dict.txt` |
| 二值化阈值 | `ocr.detection.thresh` | 0.30 | 0.30 | 0.30 |
| 文本框阈值 | `ocr.detection.box-thresh` | 0.60 | 0.60 | 0.60 |
| 文本框扩张系数 | `ocr.detection.unclip-ratio` | 1.50 | 1.50 | 1.50 |
| 识别批次 | `ocr.recognition.batch-size` | 6 | 6 | 6 |
| 文本行方向分类 | `ocr.runtime.use-cls` | false | false | false |
| 检测长边上限 | `ocr.detection.max-side-limit` / `ocr.xberg.det-limit-side-len` | 960 | 960 | **960** |
| 线程预算 | `intra-op-num-threads` / `ocr.xberg.max-threads` | 1（会话级） | 1（会话级） | **4**（进程级） |
| 并发会话上限 | `ocr.xberg.max-concurrent-ocr` | 不适用 | 不适用 | **4** |

### 5.2 Xberg 调优项

| 调优项 | 配置键 | 调优值 | 依据与效果 |
| :--- | :--- | :---: | :--- |
| 进程级线程预算 | `ocr.xberg.max-threads` | **4** | Xberg 默认为 `min(CPU 核数, 8)`，本机 16 逻辑核用不满整机；显式给足后 C=4 吞吐与延迟都优于默认（见 4.3） |
| 检测输入长边 | `ocr.xberg.det-limit-side-len` | **960** | 与 mica-ppocr / RapidOCR4j 的 `max-side-limit=960` 对齐，消除 Xberg 默认 1024 带来的多余检测像素（见 4.4） |
| 并发会话上限 | `ocr.xberg.max-concurrent-ocr` | 4 | 显式固定可消除「按空闲内存下调、首次抽取后固定」带来的不确定性；实测限制到 4 会显著压低吞吐，因此保持跟随线程预算 |

> 调优边界：以上三项只改动 Xberg 的**线程与输入尺寸**，不触碰模型档位、检测/识别超参、批次与语言，因此三家仍然跑在同一套 PP-OCRv6 `tiny` 权重与同一套 OCR 语义参数上（见 5.1），对比结论不失真。
> 效果说明：本机为 16 逻辑核桌面环境，上述调整主要收益是**去掉文档记载的线程上限、消除并发额度随机性**；单次运行的吞吐增量与环境噪声同量级（±15%），因此不应把 Xberg 与另外两家的差距归因于配置，真正差距来自 4.2 / 4.5 的会话串行与文档流水线固定开销。

## 八、 生产环境选型综合建议

1. **如果你的项目是 Spring Boot / 企业微服务，且需要处理证件、发票、营业执照等结构化数据**：
   - **首选 `mica-ppocr`**：开箱提供 Spring Boot Starter，内置 9+ 种常见凭证解析器，支持整图 4 方向纠偏（处理手机倒拍/横拍），模型与代码解耦方便升级。

2. **如果你的项目是通用工具库、或者需要精确字/词级高亮标注、或需要兼容 JDK 17 及以下**：
   - **首选 `RapidOCR4j`**：开箱内置模型，无需配置模型文件路径，支持单字/词级细粒度坐标输出，支持调用级热参数覆盖（`ParamConfig`）。

3. **如果你的项目需要多格式文档理解（PDF/Office/图片统一入口），并希望一次拿到版面、表格、分块与关键词**：
   - **首选 `Xberg`**：绑定库、ONNX Runtime 与 PP-OCRv6 模型全部打包在 `xberg-jdk21` jar 内，`Xberg.extract` 单入口覆盖图片/PDF/Office；代价是必须运行在 **JDK 21 且开启 `--enable-preview`** 的进程上，且其 PaddleOCR 后端对单页图片的并发扩展性弱于纯 OCR 库。

4. **高并发部署与资源配置建议**：
   - OCR 计算主要消耗 CPU 和 Native 物理内存（RSS），JVM 堆占用极少。
   - 容器化部署时，**内存限制（Memory Limit）必须以 Native 物理内存为基准**（建议每路并发预留 300MB~500MB 物理内存），不能仅依赖 `-Xmx`。
   - `mica-ppocr` / `RapidOCR4j`：把 `intraOpNumThreads` 设为 `1`，靠应用侧并发度扩展；把三者的 `intraOpNumThreads` 同时调到核数会造成 `C × intraOp` 超订，吞吐反而掉到默认配置的 1/4~1/6（见第四节对照实验）。
   - `Xberg`：显式设置 `concurrency.max_threads`（默认 `min(CPU 核数, 8)`，8 核以上机器用不满整机）并让 `max_concurrent_ocr` 有确定值，避免并发额度随启动瞬间的空闲内存浮动。
   - 同一 JVM 内混跑多个 OCR 引擎时，Windows 会按模块名复用已加载的 `onnxruntime.dll`；本工程先让 Xberg 落地并加载其自带 ONNX Runtime，再启动其余引擎，保证三者共享同一份原生运行时。

## 九、 复现方式

```bash
# 1. 用 JDK 21 运行（Xberg 绑定库依赖 preview 特性，JDK 17 无法加载）
export JAVA_HOME=/path/to/jdk-21

# 2. 直接启动，CommandLineRunner 会自动跑完整基准并覆写本报告
mvn spring-boot:run

# 3. 只想跑测试不跑基准
mvn test -Dtest=OcrCompareTest
```

- 运行参数由 `spring-boot-maven-plugin` 注入：`--enable-preview --enable-native-access=ALL-UNNAMED -Dxberg.runtime.dir=target/xberg-runtime`，IDE 中直接运行主类时需手工补上。
- Xberg 的绑定库 / ONNX Runtime / PP-OCRv6 模型全部来自本地仓库的 `io.xberg.jdk21:xberg-jdk21:1.3.9`，首次运行落地到 `target/xberg-runtime`，也可用环境变量 `XBERG_RUNTIME_DIR` 改写。
- 调整基准规模：`ocr.benchmark.requests-per-bench`、`ocr.benchmark.warmup-requests`、`ocr.benchmark.stability-requests`、`ocr.benchmark.concurrencies`。
- 只做单测不跑基准：`ocr.benchmark.auto-run-on-startup=false`。
